API de Crédito com Java

API fictícia de análise de crédito com testes de regras de negócio, respostas HTTP e documentação, contemplando valores de fronteira e entradas inválidas.

  • 35 testes automatizados
  • Swagger interativo
  • CI/CD

Java 17 · RestAssured · JUnit 5 · Gradle · Gson · OpenAPI · Swagger UI · Docker · GitHub Actions · Render

Ver detalhes técnicos

Regras e cenários

Validação de idade, renda mensal e valor solicitado, com critérios fictícios de aprovação. Os cenários verificam aprovação, reprovação, campos obrigatórios, valores de fronteira e requisições inválidas. Os valores monetários são tratados com BigDecimal.

Estratégia de testes

Suíte com 35 testes: 19 testes unitários das regras de negócio, 8 testes HTTP da análise de crédito, 7 testes HTTP da documentação e 1 teste HTTP inicial de verificação do ambiente. Os testes da API iniciam o servidor local automaticamente.

Integração e implantação contínuas

O GitHub Actions executa os testes e disponibiliza os relatórios. Após a aprovação da etapa de testes, o workflow solicita o deploy do commit testado por um Deploy Hook. O Render constrói e executa a aplicação em Docker.

Demonstração interativa

A interface Swagger UI utiliza uma especificação OpenAPI para apresentar os endpoints e permitir o envio de solicitações fictícias pelo navegador. Os testes verificam o HTML servido e campos selecionados da especificação.

Automação web

Automação de um sistema legado

Estruturação de uma automação do zero para um sistema legado de cartões de crédito, com foco em organização e reutilização de código.

Python · Selenium · Behave · Page Objects

Ver estudo de caso

Contexto e desafio

O trabalho envolveu iniciar a estrutura de automação de uma aplicação legada e organizar a interação dos testes com os elementos da interface.

Minha atuação

Estruturei a automação com Page Objects, herança e métodos reutilizáveis. Na classe PageHelper, utilizei esperas explícitas com WebDriverWait e tempos de espera recebidos como parâmetro.

Entrega e colaboração

Implementei a estrutura inicial e orientei uma colega QA no desenvolvimento de testes utilizando essa base, compartilhando a organização e o funcionamento do código.

Investigação de falhas

Falha de isolamento entre produtos

Identificação de uma inconsistência em uma regra de desativação, com risco de um evento de um produto afetar indevidamente dados de outro.

SQL · Análise de regras de negócio · Testes de integração

Ver estudo de caso

Contexto e desafio

Em um fluxo com diferentes produtos financeiros, era necessário verificar se a desativação de dados respeitava o produto associado ao evento.

Minha atuação

Durante a validação em homologação, identifiquei o comportamento incorreto e investiguei os registros no banco de dados, confrontando o resultado com a regra de negócio esperada.

Falha identificada e risco

A investigação revelou o risco de a operação desativar dados de outro produto, além daquele relacionado ao evento. O caso demonstrou a importância de validar os efeitos da operação nos demais produtos.

Validação de APIs e eventos sob carga

Execução de requisições automatizadas e conferência do processamento dos eventos, com apoio de serviços AWS.

Newman · AWS Lambda · DynamoDB · CloudWatch

Ver estudo de caso

Contexto e desafio

O teste exigia acompanhar o comportamento das APIs sob carga e conferir a entrada dos eventos, indo além da resposta de cada requisição.

Minha atuação

Utilizei scripts Newman executados por AWS Lambda para disparar as requisições. Consultei o DynamoDB para conferir os eventos e acompanhei os logs no CloudWatch.

Verificações realizadas

Acompanhei os tempos de processamento, a utilização de CPU dos componentes monitorados e os registros de execução, reunindo informações para analisar o comportamento do fluxo durante o teste.
