Automação Web com Python

Automação de um simulador fictício de crédito com Selenium, validando aprovação, reprovação, campos obrigatórios, mensagens de erro e limpeza do formulário.

  • 24 testes web
  • Page Objects
  • CI com Chrome

Python · Selenium · pytest · WebDriverWait · pytest-html · FastAPI · Uvicorn · GitHub Actions · Render

Ver detalhes técnicos

Cenários e verificações

Suíte com 24 testes que contemplam aprovação, valores de fronteira, reprovação por múltiplos critérios, campos obrigatórios, entradas inválidas, separadores decimais e limpeza do formulário. As verificações incluem mensagens, foco e indicação de campos inválidos.

Organização da automação

Page Objects separam os cenários dos localizadores e das ações da interface. A BasePage centraliza interações reutilizáveis e esperas explícitas com WebDriverWait. Cada teste utiliza uma nova sessão do Chrome.

Execução independente

O repositório inclui a aplicação demonstrativa. Por padrão, as fixtures iniciam o servidor em uma porta local disponível e o encerram ao final da sessão. Após instalar as dependências, a suíte é executada com um único comando, sem iniciar outro projeto.

Relatórios e evidências

A execução gera relatórios HTML e JUnit XML. Em falhas de preparação ou execução, quando o navegador está disponível, uma captura de tela é anexada ao relatório e salva também como arquivo PNG.

Integração contínua e demonstração

O GitHub Actions executa os testes em Linux com Chrome em modo headless e disponibiliza os relatórios como artefato. A aplicação demonstrativa está publicada separadamente no Render para exploração manual. Os testes do CI utilizam sua própria instância local.

Automação Web com Java

Automação de um simulador fictício de crédito com Selenium, validando regras de negócio, campos obrigatórios, entradas inválidas e comportamento do formulário.

  • 25 testes automatizados
  • Page Objects
  • CI com Chrome

Java 17 · Selenium · JUnit 5 · Gradle · WebDriverWait · BigDecimal · Gson · Swagger UI · Docker · GitHub Actions · Render

Ver detalhes técnicos

Cenários e verificações

Suíte com 25 testes: 24 cenários do simulador e 1 teste de verificação do ambiente Selenium. Os cenários contemplam aprovação, reprovação, valores de fronteira, múltiplos motivos, campos obrigatórios, entradas inválidas, formatos decimais e limpeza do formulário.

Organização da automação

Page Objects encapsulam os localizadores e as ações da interface. A BasePage centraliza interações reutilizáveis e esperas explícitas com WebDriverWait. Os testes utilizam JUnit 5, parametrização e uma nova sessão do Chrome para cada cenário.

Execução independente

O projeto inclui sua própria aplicação Java, com HttpServer do JDK e regras monetárias implementadas com BigDecimal. Os testes do simulador iniciam o servidor em uma porta local disponível e o encerram ao final de cada classe, sem depender dos outros projetos ou do Render.

Relatórios e evidências

O Gradle gera relatórios HTML e JUnit XML. Uma extensão do JUnit tenta capturar a tela quando ocorre uma falha de preparação ou execução, antes do encerramento do navegador. Os PNGs são salvos separadamente do relatório HTML.

Integração contínua e hospedagem

O GitHub Actions executa os testes em Ubuntu, com Java 17 e Chrome em modo headless, disponibilizando relatórios e evidências como artefatos. A aplicação demonstrativa está hospedada no Render em uma imagem Docker, com simulador e documentação Swagger. Os testes do CI utilizam sua própria instância local.

Automação web

Automação de um sistema legado

Estruturação de uma automação do zero para um sistema legado de cartões de crédito, com foco em organização e reutilização de código.

Python · Selenium · Behave · Page Objects

Ver estudo de caso

Contexto e desafio

O trabalho envolveu iniciar a estrutura de automação de uma aplicação legada e organizar a interação dos testes com os elementos da interface.

Minha atuação

Estruturei a automação com Page Objects, herança e métodos reutilizáveis. Na classe PageHelper, utilizei esperas explícitas com WebDriverWait e tempos de espera recebidos como parâmetro.

Entrega e colaboração

Implementei a estrutura inicial e orientei uma colega QA no desenvolvimento de testes utilizando essa base, compartilhando a organização e o funcionamento do código.

Investigação de falhas

Falha de isolamento entre produtos

Identificação de uma inconsistência em uma regra de desativação, com risco de um evento de um produto afetar indevidamente dados de outro.

SQL · Análise de regras de negócio · Testes de integração

Ver estudo de caso

Contexto e desafio

Em um fluxo com diferentes produtos financeiros, era necessário verificar se a desativação de dados respeitava o produto associado ao evento.

Minha atuação

Durante a validação em homologação, identifiquei o comportamento incorreto e investiguei os registros no banco de dados, confrontando o resultado com a regra de negócio esperada.

Falha identificada e risco

A investigação revelou o risco de a operação desativar dados de outro produto, além daquele relacionado ao evento. O caso demonstrou a importância de validar os efeitos da operação nos demais produtos.
